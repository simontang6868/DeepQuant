## 0. 结论（先行）

**主判定：`RULE_VERSION_UNRESOLVED`（价格过滤规则版本未解决）**

冻结文档（`SP5_预登记.md` §2、 `forward/sp4_config_v1.json`）写明 **价格过滤 1~50 元**，但产生全部 SP-5 机制数字的真实回测引擎（`build_panel.py:190` `between(1.0,200.0)`、`sp3_entry_rule.py:25` `PRICE_MAX=200.0`）实际执行的是 **1~200 元**。两套前瞻系统进一步互相矛盾：

- `scripts/audit/sp4_forward.py`：**配置驱动**，读 `sp4_config_v1.json` 的 1-50，并对配置哈希做断言（`assert want==got`）；
- `scripts/sp5/p13_forward.py`：**硬编码** `CLOSE_HI_MAIN=200.0` 为"主口径"，1-50 仅作对照列。

原始证据不足以唯一确定"正式规则"究竟是哪个。按专家任务书第三.(6) 条，输出 `RULE_VERSION_UNRESOLVED`：**保留 1-200 与 1-50 两个口径作为独立版本，暂停将其合并成同一策略的正式样本外结论。**

> **这不是"因为影响小所以无关紧要"。** 影响小（见 §3）只说明该冲突未污染 target selection，但**不解决规则版本归属问题**。规则 6 明确禁止"与历史回测一致就代表选择合理"的默认认定。

## 2. 当前主口径（1-200）是否属于"事后规则修改"？

**判定：是"口径选择"，但因冻结文档与引擎冲突，该选择未被授权为唯一正式规则。**

- 证据链：前瞻决策代码 `p13_forward.py` 在**首次运行前**即已硬编码 `CLOSE_HI_MAIN=200.0`，并非看到结果后改动 → 不满足"看到结果后改规则"（预登记 v1.1/v1.2 的修订均满足此定义）。
- 但：冻结文档（预登记 + config）明确写 1-50，且预登记 §6 禁止"修改策略参数"，§9 要求启动校验哈希。前瞻选 1-200 既**偏离冻结文档**，又**未走"出新版本预登记"流程**（预登记只在新窗口/新判定时出 v1.x，未就价格过滤出过 v2）。
- 故：1-200 是"回测实际口径"的合理继承，但**未经正式规则变更程序**，不能据此宣称"前瞻与冻结规则一致"。

**结论**：价格过滤是 genuine 的 `RULE_VERSION_UNRESOLVED`，不因"前瞻选了回测值"而消解。

## 7. ⚠️ 更正说明（2026-10-26 22:5x 追加，原文 §3 不改写）

**触发**：P0-3 门禁审计发现 `forward/ledger/20260930.json` 里 `target_holds`（1-200 主口径）与 `target_holds_close50`（1-50 对照）**完全不同**——`603193/301336/301202/000597/002692` vs `603135/300946/000715/600713/600055`，而 §3 称"top5 在 4 个截面均 100% 一致"。二者不可能同时成立，故用前瞻系统**自身实现**（`p13_forward.build_snapshot` + `p13_forward.pick`）重算。

**结论：§3 的「top5 5/5 一致、对持仓无影响」是方法错误导致的漏检，作废。**

### 7.1 错在哪

§3 的复算在 `panel_monthly.parquet` 上沿用了面板里按 **1-200 宇宙**预计算的 `f3pct / liqpct` 分位列，再按价格上限筛选。但 `p13_forward.pick()` 的实际做法是：

```python
g = s[s["ok_buy"]]                      # 先按价格上限过滤
g["f3pct"] = g["f3"].rank(pct=True)      # 再在过滤后的子集内重算分位
g["liqpct"] = g["amt20"].rank(pct=True)
pool = g[(g["f3pct"] <= 0.70) & (g["liqpct"] < 0.20)]
```

**分位分母随宇宙改变**。价格上限从 200 收到 50 会剔除 513 只股票，分位排名随之变化，临界个股的入选状态会翻转。§3 沿用旧分位，等于把 1-50 的池当成 1-200 池的子集来比，必然得到"几乎一致"。

用同一份 20260930 截面复核该机制（`sp5_out/p13d_pool_overlap.json`）：

| 复算方式 | 1-50 池 | 与 1-200 池交集 | top5 |
|---|---:|---:|---|
| **旧方法**（沿用 1-200 分位） | 749 | 749 | 与 1-200 **完全相同** |
| **正确方法**（子集内重算分位） | 686 | 686 | 与 1-200 **0/5 重合** |

旧方法精确复现了 §3 的"一致"结论——这本身就是错误来源的指纹。

### 7.2 正确数字（4 个截面，权威实现）

| 20260430 | 5,109 / 4,476 | 756 / 644 | 112 | **0/5** | 0/5 |

### 7.3 机制（为什么池只差 72~125 只，top5 却全换）

- 1-50 的池**完全是** 1-200 池的子集（only_50 = 0，Jaccard 0.905）；差异是 1-200 多出 72 只。
- 1-200 的 top5 收盘价分别是 20.25 / 41.67 / 35.64 / 4.76 / 4.22 元——**全部 ≤50，不是被价格直接排除**。
- 它们的 `liqpct` 分别是 **0.1996 / 0.1993 / 0.1991 / 0.1989 / 0.1987**，距 0.20 阈值仅 0.0004~0.0013。
- 剔除 513 只高价高换手股后，这 5 只的 amt20 分位排名整体上移，**全部越过 0.20 被排除**；于是 1-50 只能退而取池内 amt20 最高的另一批（amt20 ≈ 4,860~4,882 万）。
- 也就是说：`entry_rule`（池内 amt20 降序取前 5）实质是「在流动性分位 20% 线**下方**取换手最高的 5 只」，目标恰好密集分布在该临界线上 → 对宇宙定义极度敏感。

3. **§6 第 3 条作废**：原文"V-B 其 target 与 V-A 当前完全一致（5/5），两版本观察期初期结论将重合"——**错误**，实测 0/5。
