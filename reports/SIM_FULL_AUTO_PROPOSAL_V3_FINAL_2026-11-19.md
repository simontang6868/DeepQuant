## 1. 不可协商的六道门（E0 新增）

| 门 | 判据 | 失败动作 |
|---|---|---|
| **E0** | 系统真实时钟与 `EXEC_DATE×FIRST_ORDER_TIME` 偏差 ≤10min，且 `NTPSynchronized=yes` | FAIL/停机，落盘 `CLOCK_FAIL` |
| E1 | `ledger/20261130.json` 存在、`mode=FORWARD`、`target_holds_d4` 非空、sha 与旁证一致 | rc=4，零报单 |
| E2 | DRYRUN `20261127` + preflight `20261130` 产物存在且完整 | rc=4 |
| E3 | 授权守卫 ALLOW 6/6（每次报单前重校） | rc=4 |
| E4 | 隔离 FAIL 0 + 清单 59/59 + **旁证三条件**（见 §3） | rc=4 |

**E0 动机（专家新发现，须写入新预登记）**：授权 `not_after=2026-12-02T23:59:00+08:00`，意图时点是单一点 `12-01 09:35`，时间窗约 **38 小时**。无 E0 时 E3 在这 38h 内任意时刻都判 PASS；加 ±10min 后收窄至 20min。**E0 不是纵深防御，是唯一的时间精度门控。**

门限逻辑（专家裁决 1）：门限宽窄与"错日执行"无关（错日是小时/天级，任何门限都拦得住）；±10min 只决定"迟到多少算失败"，timer 抖动为秒级、NTP 已同步漂移毫秒级，±10min 宽裕 2~3 个数量级。**不得调宽；任何调宽须新预登记。** NTP 前置实测（2026-11-19）：云端 `Timezone=Asia/Shanghai`、`NTPSynchronized=yes`、chrony `System time 0.000027202 seconds slow`、`Leap status=Normal` ⇒ 前置条件当前满足。

## 2. 旁证双证据结构（专家裁决 2）

### 2.1 时序悖论的解法：冻结程序，不冻结值
预登记冻结三件事：
1. 旁证产物的**格式**（含字段、哈希算法、commit 字段）
2. **生成程序**（本机跑 E4 的脚本路径与调用方式）
3. **发布动作**：旁证生成后经 **11-30 17:40 现有 `deepquant-alert` 邮件链外发其 sha256**

程序先冻结、值后产生 ⇒ 悖论消解。锚定介质 = 离云即不可回溯改写、带邮件服务商时间戳的告警邮件。**零新增凭证、零新增服务。**

### 2.2 运行时机器可验的三条（内部一致性）
- 旁证存在且内嵌哈希与内容一致
- commit 与当前部署树匹配
- 与当前部署树**双向集合全等**（检出新增/删除/内容变化，非仅逐文件哈希）

任一不符 ⇒ FAIL，不降级为警告。

### 2.3 外部真实性：事后可检测，非事前预防
- 11-30 17:40 邮件外发旁证 sha256
- 12-02 归档邮件复载同一 sha256
- 归档脚本自动比对、账户持有人终审

**必须明示的边界**：单主机内**不存在**机器可验的外部锚（除非第二主机或外部时间戳服务）。邮件双发给出的是 **tamper-evidence（事后可检测）**，不是事前预防。这与 `SIM_DRILL` 以操作失误为主的威胁模型匹配。**若未来触及真实资金，回到方案 B（当日他证）或第三方存证**，本结构不得沿袭。

### 2.4 生成顺序（不可调换）
```
实施改造 → 部署 → manifest --write（59/59）→ 本机 E4 出证 → 17:40 邮件外发 sha
```
此后任何改动（哪怕一行注释）使旁证失效 ⇒ 重走全链。

## 3. 失败日志 schema 与哨兵四态（专家裁决 3）

### 3.1 日志（现在定义，冻结进新预登记）
固定路径：`forward/sim_exec/20261201_result.json`
写入方式：**原子写**（tmp + rename）；`try/finally` 包裹，**所有退出路径含异常必须落盘**。

```json
{
  "schema": "sim_exec_result/v1",
  "exec_date": "20261201",
  "started_at": "2026-12-01T09:35:04+08:00",
  "finished_at": "2026-12-01T09:35:09+08:00",
  "outcome": "SUCCESS | GATE_FAIL | CLOCK_FAIL | NOT_AUTHORIZED | ERROR",
  "rc": 0,
  "gates": {"E0": "PASS", "E1": "PASS", "E2": "PASS", "E3": "PASS", "E4": "PASS"},
  "n_real_orders": 0,
  "corroboration_sha256": "<旁证哈希>"
}
```
`started_at/finished_at` 必须记**真实系统时钟**——这同时是 E0 的事后复核证据。

### 3.2 哨兵四态（v2 只列三态，此处补全）
| 状态 | 判读 | 动作 |
|---|---|---|
| 存在且 `SUCCESS` | OK | 无告警 |
| 存在且非 `SUCCESS` | 失败 | 告警（带 outcome） |
| 不存在 | 演练未发生 | 告警 |
| 存在但 JSON 损坏/schema 不符 | `ERROR` | 告警，**失败关闭，不得跳过** |

## 6. 验收标准（9 条）

1. 12-01 09:35 timer 自动触发；E0 通过；五门全 PASS；`rc=0`
2. 任一门 FAIL ⇒ `rc=4` + 失败日志落盘 + 零真实委托
3. 旁证：内嵌哈希一致 + commit 匹配 + 双向集合全等（含增删检出）
4. `sim_orders/20261201.jsonl` 的 cid 双向差集逐条可解释；`n_unexplained>0` ⇒ **硬失败**
5. 18:10+ 正式对账产物存在且 `settlement_verified` 确认为后结算；`NO_INPUTS` 未触发
6. 17:10 `refonly` 产物带显式标记，不进可引集合
7. 变异 **9/9** 检出（含 M9 旁证篡改）；回归四连全绿；manifest 本地/云端 59/59 PASS
8. 未发生（哨兵）/ 未结算（T3 超时）均有告警邮件，无静默
9. **`execution_reports` 服务端时间戳全部落在 `09:35±10min` 窗口**（裁决 4 引入，对账硬失败项）
