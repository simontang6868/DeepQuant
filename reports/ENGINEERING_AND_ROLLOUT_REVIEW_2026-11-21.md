## 3. 端到端链路：从信号到对账

### 3.1 链路总图

```
[11-30 17:10] 日更链 daily_chain.sh
   └→ p13_forward.py: 生成 forward/ledger/20261130.json
        含 mode=FORWARD、target_holds_d4（D4 严格口径）、ref_close_d4（同源价格映射）
   └→ 17:40 告警邮件携带旁证 sha256（tamper-evidence 锚）
   └→ 旁证冻结（sim_corroboration --build）

[12-01 09:35] sim-exec.timer → sim_rebalance_executor.py --execute
   E0 时钟（必须在意图窗口内 + NTP）
   E1 台账（存在 + mode=FORWARD + d4 非空 + 每个 d4 目标有正有限价）
   E2 演练产物（DRYRUN_20261127 + PREFLIGHT_20261130 双存在）
   E3 授权（paper_authorization.json 的 scope/额度/有效期，守卫判 ALLOW）
   E4-CORROB 旁证（sha 与冻结值一致）
   E4 隔离/清单（通道隔离 PASS + manifest 65/65）
   ── 全 PASS → 实例化 GmTradeBroker → order_volume 限价下单
   ── 任一 FAIL → rc=4，零报单，落 GATE_FAIL 结果

[12-01 09:45] 哨兵 sim_exec_result --sentinel
   MISSING / CORRUPT / STALE / FAILED / SUCCESS 五态

[12-01 18:10] 对账 sim_reconcile
   注：掘金 18:00 才结算，17:10 取的是"收盘后结算前"快照，故对账必须 18:10+
```

### 3.2 关键设计：门控"失败关闭"

- 六门**全部**通过才实例化真实 broker。任一失败 → 不构建计划、不下单、写 `GATE_FAIL`。
- 所有退出路径经 `main_logged` 包装，保证**原子落盘**（tmp + `os.replace`），异常也留痕。
- **落盘门槛（方案甲）**：`write_result(path=None)` 按 `started_at` 是否在意图窗口内分流——窗口外落 `.TEST_<stamp>.json`，窗口内才落生产名 `20261201_result.json`。防止"手工试跑污染生产结果"。

### 3.3 已知技术约束（实盘同样适用，务必审查）

| 约束 | 影响 | 缓解 |
|---|---|---|
| gmtrade **无行情接口** | 无法盘中重定价；价格只能用台账 `ref_close_d4`（11-30 收盘价） | 限价单一次性提交，未成交则 CARRY 顺延；预登记已登记该限制 |

## 6. 实盘交易路径（与模拟盘的本质差异）

### 6.1 四层差异（必须逐层切换，不能只改一处）

| 层 | 模拟盘（现在） | 实盘（目标） |
|---|---|---|
| **账户** | 掘金仿真账户（`account_id` 为仿真） | 真实券商账户（需券商开通程序化交易权限） |
| **授权文件** | `paper_authorization.json`（`channel=gm-paper`，`max_notional=100000`） | 需**独立** `live_authorization.json`；当前被隔离检查**列为禁止文件名**，说明设计上尚未允许 |
| **资金** | 10 万仿真额度 | 真实资金，需按整手/佣金下限重新测算最小可行规模 |
| **合规责任** | 无 | 投资者适当性、程序化交易报备（视券商与监管要求）、异常交易监控 |

### 6.2 前置条件清单（硬性，缺一不可）

1. **券商程序化交易权限**：gmtrade 实盘 API 权限（不是仿真），需券商审批。
2. **独立实盘授权文件**：`live_authorization.json`，字段与 paper 版同构但语义更严（额度、标的范围、有效期、熔断阈值）。
3. **隔离检查从"禁止"升级为"强校验"（不是移除）**：`check_channel_isolation.py` 当前把 `live_*` 当禁止项，这是**防止误配实盘的最后一道墙**，拆掉等于把风险敞口从 0 拉到 1。正确做法是把判据从「禁止存在」改为「**存在时必须同时满足**：双人签名 + 额度上限 + 审计日志 + 独立服务账户」，即**改判据、不删判据**。需新预登记冻结新判据。
4. **`LIVE_ENABLED=true`**：云端 env 显式改值，且改动必须有审计记录（谁、何时、依据哪份授权）。
5. **资金到位与规模测算**：见 §6.4。
6. **风控阈值重设**：`max_notional`、单票上限、单日换手上限、熔断线。
7. **监控与告警升级**：实盘异常必须有人接（当前告警是邮件，实盘建议加短信/电话）。
8. **回滚预案**：一键停止（disable 全部 timer + 券商端撤单 + 导出持仓快照 + 锁定对账口径）。**必须在首次实盘前实演一次**，而不是只写在预案里——没演练过的回滚预案等于没有。

### 6.3 代码改动点（技术上是小改动，流程上是大事）

| 改动点 | 现值 | 实盘值 | 风险 |
|---|---|---|---|
| `account_id` / `endpoint` | 仿真账户 / `api.myquant.cn:9000` | 实盘账户 / 实盘 endpoint | 配错会打到错误账户 |
| `LIVE_ENABLED` | `false` | `true` | 这是"总闸"，改它等于解除全部仿真保护 |
| 授权文件 | `paper_authorization.json` | `live_authorization.json` | 需新的 guard 分支 |
| 隔离检查规则 | 禁止 `live_*` | **升级为强校验**（双人签名+额度+审计+独立账户），不删判据 | 改判据要新预登记，不能偷偷删 |
| 资金常量 | `CAPITAL=100000` | 真实资金 | 影响整手抽样率与成本占比 |

> **关键判断**：技术改动量很小（几处配置 + 一个 guard 分支），**但这恰恰是危险所在**——"改几行就能上实盘"意味着误操作成本极高。因此必须用"预登记 + 授权 + 双人复核"把流程约束做厚，而不是靠代码复杂度兜底。

### 6.4 资金门槛（决定"能不能做"的硬约束）

核心矛盾：**A 股整手（100 股）+ 佣金 5 元下限**，两个机制共同把"小资金"挡在门外。

**机制一：整手约束**。单票金额 ÷ 股价 必须凑成 100 股整数倍，凑不满的部分变成闲置现金。

以 **10 万 × 20% 仓 ÷ 5 只 = 每只 4,000 元** 计（`STATUS.md:81` U-5 口径）：整手**闲置率** 12.0%（期望）/ **8.9%（抽样实测）**——注意这是"投不出去的现金比例"，不是"抽样率"。20% 目标仓实际只有 8.11% → **7.50~7.66%**，达不到 8% 门槛。

> 只数很关键：10 万 ÷ 4,000 = 25，但策略只持 **5 只**，所以每只 4,000（不是 10 万÷25）。读者不要按"总资金÷单只金额"反推只数。

**机制二：佣金 5 元下限**。单笔金额小时，5 元最低佣金吞噬收益。万 2.5 全佣下，单笔需约 **12.5 万**才能让费率真正生效；按 4,000 元/只测算，显性成本 **0.302% 往返 ≈ 回测口径的 3 倍**。

**机制三：规模效应**（引用 `memory/RESULTS_INDEX.md`，本轮未复核）。整手影响随资金上升快速衰减：100 万量级仍有 **+2.5pp** 级影响，3,000 万降至 **+0.033pp/月**，1 亿 **+0.012pp/月**——但此时成本与市场冲击成为新瓶颈。

> 结论：**10 万以下不建议实盘做多标的分散策略**（整手抽样严重偏离目标权重）；**30 万~50 万是较现实的最小起步区间**；1,000 万以上整手不再是瓶颈，但成本与冲击成为主要约束。
> ⚠️ 上述百分比来自不同口径的历史测算（含 20% 仓位假设），**不可直接套用到你的实际参数**；实盘前必须用真实股价分布与目标标的数重算一次。

### 6.6a T6 缺陷的影响面（审查意见第一条的完整回答）

审查者问「T6 的 ffill 会不会污染成本后 alpha」。为此做了代码级核查，结果比设想的更严重，分三层：

**第一层：初稿引错了策略线。** `+0.1360pp/月` 属 **exQ5 线**，非所交易 d4（已在 §6.5 更正）。即使它被污染，也与 d4 无关。

**第二层：所交易策略的回测引擎里也有同一个 ffill。**

| 文件 | 行 | 用途 | 是否被 T6 检查 |
|---|---|---|---|
| `p04_position_dd.py` | 219 | 逐日盯市净值 | ✅ 是（T6 就查它） |

**第三层：ffill 的影响（按二轮预审收窄，不夸大）。** ffill 用停牌前价延续，把停牌期间的下跌**推迟到复牌日**：

- **收益的时点被扭曲**：下跌不在停牌期体现，而在复牌日集中体现；
- **月末停牌股估值**偏离可成交价 ⇒ 月收益可能失真；
- **对 MDD 的方向不能一概而论**：峰谷总跌幅未必改变（取决于停牌与复牌的价格路径），所以**初稿"MDD 必然被低估"是过度推断，已撤回**。

**补充：比 ffill 更明确的偏差是幸存者偏差。** `p03d_d4_strict.py:75` 用 `panel["fwd20"].notna()` 筛候选池——只有"后来 20 个交易日有数据"的股票才可能入选，等价于**排除后来退市/长期停牌的股票**。`p13_forward.py:13` 自己写明这点。方向是**系统性高估**，比 ffill 的方向更确定。

> 另需注意：初稿引用的"某窗口 −40.69% → 修正后 −42.99%"出自 TDX 的买入持有实验（`TDX_W6/W7`），**不是 p03d**；跨实验外推不成立，已删除该论据。

**结论：T6 不是"P1 可延后"，而是实盘经济性判断的前置阻塞。** 修正范围应覆盖 `p03d`/`p03`，不只是 `p04`；修正前 §6.5 的 d4 数字只能当上限。

> 这也再次印证项目铁律「**没检出 ≠ 没问题**」：T6 通过静态检查 p04 发现 ffill，但另外两个文件存在同样模式而**测试没覆盖**——测试的"红"只标出了它看得见的那一处。

### 6.7 建议的分阶段上线路径

| 阶段 | 资金 | 标的数 | **本阶段预期收益** | 验证目标（价值所在） | 通过标准 | 观察期 |

### 6.8 实盘特有风险与控制

| 风险 | 后果 | 控制 |
|---|---|---|
| 无行情接口 ⇒ 限价单挂出后无法跟踪 | 未成交不知情，次日才发现 | 哨兵 + 次日对账；限价单偏保守 |
| 无 `client_order_id` ⇒ 重复下单 | 超买/超卖 | **⚠️ 本地幂等是进程内存，崩溃重启即失效**（初稿低估了）。必须加**意图落盘**，见下方 |
| 停牌/涨跌停导致无法成交 | 目标权重偏离 | 已有"不可成交跳过"逻辑；需监控偏离度 |
| 结算时点错配 | 对账失真 | 18:10 后对账 |
| 程序化交易合规 | 监管风险 | 券商报备、异常交易监控、留痕 |
| 总闸误开 | 灾难性 | `LIVE_ENABLED` 双人复核 + 变更留痕 |

**无 `client_order_id` 的真实危险场景（审查意见指出的关键路径）**：

```
发单成功 → 回报超时 → 进程认为失败退出
        → 人工看日志以为"没成" → 手工重跑 → 重复下单
```

内存幂等挡不住"崩溃 + 人工介入"这个组合。**建议的加固（实盘前必须做）**：

1. **发单前**写 `intent_<stamp>.json`（订单参数 + 时间戳 + 目标持仓快照）；
2. **发单后**写 `sent_<stamp>.json`（回报原文 + order id）；
3. **任何启动**（含人工重跑）先跑 reconcile：比对 `intent` 与 `sent` 与券商实际委托/持仓，缺 `sent` 的 intent 一律先查单再决定，不得直接重发。

> 这在仿真盘无所谓（钱是假的），**实盘是超买/超卖**。建议列为 S1 之前的前置改造项。

### 8.1 问题 4 的真实依赖链（按二轮预审收窄）

初稿说"签字人未定 ⇒ 11-25 PROBE 应暂缓"，**这个推断过强，已撤回**。核实后的事实是：

- **PROBE 已有书面授权**：`docs/PROBE_EXEC_PREREG_2026-11-20.md` 引用 `FULLAUTO_GO_statement_2026-11-20.md`，判据 P1 要求授权守卫 `ALLOW 6/6`（云端实测通过）。PROBE 是 2 只×1 手的**仿真**委托，零资金风险。
- **因此 PROBE 不需要"资金担责方"另行签字**——它的授权链是完整的。

**真实的依赖链是**：

```
签字人（11-27 go/no-go 的决策人）—— 11-24 前必须指定
   ⇒ 11-27 go/no-go 才有合法决策主体
   ⇒ 否则 12-01 顺延
```

**结论**：签字人是 **11-27 go/no-go 的前置**（因此建议 11-24 前定），**不是 PROBE 的前置**。PROBE 可按时启动；但若到 11-27 仍无人有权判 go/no-go，则 12-01 必须顺延——那时 PROBE 的结果只能留作下次使用。

### 8.2 治理断点（审查意见的最后一句，我认为最重要）

现有纪律（预登记 → 授权 → 门控 → 旁证 → 对账）**只约束了技术执行方**，尚未约束决策方。三处断点：

| 断点 | 现状 | 补法 |
|---|---|---|
| 签字人 | 未定 | 11-24 前书面指定，须是有权承担资金后果的一方 |
| 额度 | 由账户持有人定 | 与 S1 通过标准绑定，未达标不得提额 |
| go/no-go | 靠人工评审 | 给专家/审查方**书面否决权**，与"同意权"同等 |

> 补上这三点，这套系统才从"工程可控"走到"治理可控"。这是本项目比代码更值钱的部分，也是最容易被忽略的部分。
