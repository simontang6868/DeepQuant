## 1. 逐条答复

### 1.1 第 1 条：T6 会不会污染 §6.5 的 alpha

**您的判断**：如果阶段 O 的净值也经过 p04 的 ffill，那 §6.5 的 alpha 就建立在被高估的净值上。

**核查结果分三层，第二层是我原来漏掉的。**

**第一层：您设想的直接路径不成立。**
`p04_position_dd.py` 是 sp5（d4 策略）的逐日净值模拟器，阶段 O **不 import 它**。`grep -rn "p04_position_dd" scripts/ research/` 的引用方全在 sp5 内部（`p11_exec_window.py:47`、`p15_cost_alignment.py:52`、`tests/test_p04_ledger.py:19`）。所以"阶段 O 的净值被 p04 的 ffill 污染"这条路不存在。

**第二层：但阶段 O 那条链上有一条自己的 ffill，这才是真答案。**
链路是 `阶段 O → 阶段 I build_records → 阶段 C Panels`：

| 位置 | 事实 |
|---|---|
| `scripts/run_phase_c.py:234` | `self.ffill = close.ffill()`——注释写明这是"前瞻收益用的 ffill 价" |
| `scripts/run_phase_c.py:257-258` | `p0 = self.ffill.iloc[pos]`、`p1 = self.ffill.iloc[nxt]` ⇒ `fwd = p1/p0 − 1` |
| `scripts/run_phase_i_exq5.py:357-360` | 用同一个 `panels.ffill` 算 `fwd`，`fm = np.isfinite(fwd)` 筛池 |
| `scripts/run_phase_o_fee_convention.py:43` | `from run_phase_i_exq5 import build_records as build_i` |

后果：停牌横跨月末、或退市后不再有行情的股票，`p1` 取到的是**停牌前最后一价**，`fwd` 被算成 **0**，而不是 `NaN`。所以 `np.isfinite(fwd)` 和 `.dropna()` **都不会把它筛掉**——死票以"零收益"的身份长期留在池里。

⇒ **"§6.5 未受 ffill 影响"这句话我不能写。** 正确表述是：**污染路径不是 T6 检查的那条，但同类缺陷存在，且量级未测。**

**第三层：方向不能给，原因不是懒，是两条通道符号相反。**

- 若死票集中在 **Q5**（高 MAX5 ⇒ 高波动 ⇒ 退市概率更高），`r_q5` 被"0 收益"抬高 ⇒ `r_bench = fwd.mean()` 抬高 ⇒ `alpha = r_ex − r_bench` 被**压低**（结论偏保守）；
- 若死票集中在**多头腿**（非 Q5），则 `alpha` 被**抬高**（结论偏乐观）。

这个项目已有三次"机制直觉错、可算量对"的记录（C-2/C-3/I），我没有资格在这里凭直觉给符号。**所以只登记缺陷、不给方向、给可执行的量化方案**（§6.6a 第四层）：F0 现状 / F1 严格（缺口 > 20 交易日则 `fwd=NaN` 并剔出当期池）/ F2 悲观（退市记 −100%），判据写死为"三档下 `net_pp` 的符号与显著性是否一致"。

**最后要说清优先级，避免您以为我在夸大**：`+0.1360` 早已被 `DEEPQUANT_WEEKLY_REVIEW_2026-11-15.md:309` 列入"**不可引用于实盘背书**"清单。所以量化它**不改变 d4 的决策**，只决定"旁证这一项能不能引"。**优先级排在 T6 之后**——T6 修的是所交易策略（d4）自己的回测数字，那才是决策依据。

### 1.4 第 4 条：无 `client_order_id` 的幂等风险

**接受，而且核实后比您指出的更严重。您担心的是"内存幂等撑不住崩溃+人工介入"，实际代码是"落盘发生在整批发单之后"。**

| 位置 | 代码事实 | 后果 |
|---|---|---|
| `scripts/sim_rebalance_executor.py:816-818` | `for it in plan: broker.place_limit_order(...)`，结果只累积在内存列表 `out` | 循环中任一笔抛异常/进程被杀，**前面已成交的委托记录一并丢失** |
| `scripts/sim_rebalance_executor.py:820` | `n = append_orders(path, out)` 在**循环之后**才执行 | 崩溃窗口 = **整个发单循环**，不是一个函数调用 |
| `scripts/sim_rebalance_executor.py:476-481` | `gmtrade.order_volume` 签名无 `order_remark`/`client_order_id`，注释已承认 cid 无法透传 | 服务端**没有**去重依据，只能靠本地文件 |

⇒ 您设的场景不止成立，还多一层：**在落盘之前，任何一次崩溃都会让已发出的单在本地无记录**。此时人工重跑，`append_orders`（`:506`）的 cid 去重**没有任何东西可比对**，必然重复下单。

**加固方案（已写进 §6.8，4 步）**：

1. 发单**前**写 `intent_<stamp>.json`（订单参数 + 时间戳 + 目标持仓快照）并 `fsync`；
2. **每笔**发单后立即（不是整批结束）追加一条 `sent_<stamp>.jsonl`（回报原文 + order id），同样 `fsync`；
3. 任何启动（含人工重跑）先 reconcile：比对 `intent` / `sent` / **券商委托列表**，缺 `sent` 的 intent 一律先查单再决定，不得直接重发；
4. 代码改动很小（把 `append_orders` 从 `:820` 移进 `:816` 的循环 + 新增 intent 前置写），但**改变执行行为**，须走变更登记 + 全量回归 + 变异 M-IDEM。

**一处补充，防止"加了落盘就安全"的错觉**：因为 `gmtrade` 无法透传 cid，**服务端永远不会去重**。所以第 3 步的 reconcile 必须查"券商委托列表"，不能只查本地文件——本地文件只能证明"我打算发什么"，不能证明"实际成了什么"。这是按您第 5 条的逻辑做的：**护栏要加厚，不是换个位置。**

**为什么不现在改**：仿真盘无资金风险，且 12-01 前改执行路径会改变"演练对象"本身（等于把要验的东西换掉）。建议 **11-24~11-27 空窗**或 **12-02 后**改，**S1 实盘前必须完成**。
