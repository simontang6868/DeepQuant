## 1. 先说清落地边界

### 1.1 语料为什么必须是"真跑"而不是"造日志"

影子复盘的对象是操作日志。如果日志由脚本拼出来（"假装 alice 先查清单再回测"），
基线学到的是脚本的作者习惯，命中率评估也变成自证：注入器与日志生成器出自同一份
想象。因此语料走完整链路：

```
TestClient(真实 FastAPI app)  →  真实回测引擎 / 持久化  →  T1 审计中间件  →  分片 JSONL + 哈希链
```

每个会话都带 `X-Operator` 与 `X-Session-Id`，工件由中间件自动落盘，事后用
`AuditStore.iter_all()` 读回。语料本身可校验：`corpus/index.jsonl` 的链校验
（`AuditStore.verify()`）在 T1 测试中已覆盖，本轮未改动。

### 1.2 引导语料不是历史语料（这条必须写进任何引用）

| 事实 | 影响 |
|---|---|
| 150 个会话、423 张卡片全部在 **2026-10-27 同一天**生成 | 小时维度（`off_hours`）**必然停用**：语料跨度 0 小时，无法定义"工作时段" |
| 操作类型只有研究平台 6 个核心操作中的 5 个（`audit.replay` 未产生） | 覆盖不到"查询审计"这类只读操作；委托域 4 个操作**本仓库不存在**（计划 §10-1 未决） |
| 会话类型由 11 个模板按权重抽样，不是真实用户行为 | 基线的"常见流程"是本项目对研究平台的合理建模，**不是**实测习惯 |

引用本文件任何数字时，必须同时说明"语料为单次构建的引导语料（bootstrap）"。

## 2. 基线：把"正常长什么样"写成可复现的结构

### 2.1 内容

| 维度 | 内容 |
|---|---|
| 频率 | 操作 1/2/3-gram 的出现次数与会话支持数；Top-10 高频序列 |
| 顺序 | 相邻操作转移计数（谁后面通常跟谁） |
| 条件模式 | 每个操作的状态分布、原因码分布、参数骨架摘要集合、耗时 p50/p90/p99 |
| 上下文 | 操作人集合、出现小时集合、整体拒绝率、带终态操作的会话占比 |

### 2.2 可复现的三条实现约束

1. **摘要不含时间/路径/机器名**：`baseline_digest` 只覆盖内容，且排除 `generated_at`、
   `note`、`baseline_digest` 自身。踩过一次坑：摘要覆盖了自己 → 保存值与重算值永远
   差一轮，`load` 必然报"被改动过"。
2. **排序键固定**：「计数降序 + 字典序」，杜绝并列项抖动。
3. **输入顺序无关**：序列先按链上 `seq` 排序再统计。

验收时用了**两份实现**：主实现（`shadow.baseline`）与独立实现（只读 `index.jsonl`，
自己分组、自己 `Counter`）。同一份代码跑两次一致只能证明没有随机性，不能证明算对了。

### 2.3 参数骨架：为什么不直接比参数

回测参数里 `initial_cash` 每次都不同。骨架只保留结构：键集合 + **数值数量级** +
短字面量。于是 `100000` 与 `120000` 同骨架（都是 1e5），`100000` 与 `10000000`
不同骨架（1e5 vs 1e7）——后者才是"量级可疑"。标识类字符串（`run_id`、uuid、
时间戳）归一成 `str:id` / `str:timestamp`，否则"正常的新 run_id"会被报成参数漂移。

## 3. 规则：12 条，每条都能说出依据

| 规则码 | 维度 | 严重度 | 判定依据 | 启用条件（不满足则停用并登记） |
|---|---|---|---|---|
| `operator_unknown` | 上下文 | 高 | 操作人不在基线名单 | 基线 ≥2 个操作人 |
| `session_multi_operator` | 上下文 | 高 | 同一会话出现多个操作人 | 无需基线 |
| `step_order_unseen` | 顺序 | 中 | 相邻跳转在基线中计数为 0 | 基线转移总数 ≥5 且两端操作已登记 |
| `prerequisite_missing` | 顺序 | 中 | 声明式前置条件不成立（对比前需 ≥2 次回测；组合前需 1 次清单） | 无需基线（业务规则） |
| `burst_repeat` | 顺序 | 中 | 同操作 + 同请求体摘要连续 ≥4 次 | 无需基线 |
| `param_skeleton_unseen` | 条件模式 | 中 | 参数骨架摘要不在该操作的基线集合内 | 该操作基线 ≥3 次 |
| `status_unseen` | 条件模式 | 中 | 出现该操作基线未见的执行结果 | 该操作基线 ≥3 次 |
| `reject_storm` | 顺序 | 高 | 连续 ≥3 次被拒绝 | 基线拒绝率 >0 |
| `duration_outlier` | 时长 | 低 | 单步耗时 > 基线 p99 × 5 | 该操作基线耗时样本 ≥20 |
| `dangling_reject` | 会话终态 | 低 | 会话以被拒绝收尾 | 基线存在拒绝样本 |
| `flow_without_terminal` | 会话终态 | 低 | 多步操作但无任何终态产出 | 基线带终态会话占比 ≥50% |
| `off_hours` | 上下文 | 中 | 操作小时不在基线区间 | 基线小时跨度 ≥4 小时 |

两点设计说明：

- **`prerequisite_missing` 是业务规则，不是统计规律**。基线只能告诉你"这个跳转没
  见过"，说不清"这个跳转业务上不成立"；反之业务规则不依赖语料规模，冷启动当天就能用。
  两类规则互补，所以分开登记。
- **耗时阈值用相对倍数**，不用"p99 + 2000ms"这种绝对余量。快接口（十几毫秒）上
  50 倍尖峰只有几百毫秒，绝对余量会把它整个吞掉——规则在最需要它的地方失效。

### 3.1 「停用」与「未命中」必须分开

报告固定四节，第三节是**本次停用的规则（未判断 ≠ 正常）**，第四节是**已启用未命中
（判断过、正常）**。把两者混成一个"未发现异常"，就是本项目反复吃过的"没检出 ≠ 没问题"。

本轮实测：`off_hours` 全部会话停用（语料跨度 0 小时）；`duration_outlier` 对
`portfolio.backtest` 停用（基线仅 14 条耗时样本 <20），对其他操作启用。

## 4. 命中率怎么量：注入、留出、双口径

### 4.1 切分

按**会话 id 的 sha256 前缀**切 30%（150 → 训练 103 / 留出 47）。不用时间切分：
语料都在同一天，"上午训练下午测试"是假装样本外。按 id 切至少保证同一条会话
不会同时出现在两边——但它**不能**替代真正的前瞻验证，这一点写进证据的缺口清单。

### 4.2 注入 8 类语义扰动

| 类型 | 扰动 | 期望命中规则 |
|---|---|---|
| `swap_order` | 交换相邻两步 | `step_order_unseen` |
| `drop_step` | 删掉中段一步 | `step_order_unseen`（或 `prerequisite_missing`） |
| `insert_rare_op` | 插入本会话没做过的最冷操作 | 顺序/参数/状态类 |
| `status_flip` | 某步改成被拒绝 | `status_unseen` / `dangling_reject` |
| `reject_burst` | 连续 3 步被拒绝 | `reject_storm` |
| `param_drift` | 参数数量级抬高两位 | `param_skeleton_unseen` |
| `operator_swap` | 某步换成陌生操作人 | `operator_unknown` |
| `duration_spike` | 某步耗时 ×50 | `duration_outlier` |

三条防作弊措施：

1. **注入不写回工件库**。改写卡片会破坏 T1 哈希链——破坏链是篡改证据，不是业务异常，
   混进"异常样本"会让评估失去意义。注入只作用于内存序列副本，并打 `injected` 标记。
2. **空操作重抽并计数**。判据分两种：
   - 顺序类（`swap_order`/`drop_step`）以**操作顺序是否变化**为准。交换两个只有参数
     不同的同名步骤，流程视角什么都没发生，把它算作"未命中"等于让检测器去抓一个
     不存在的顺序异常。本轮 `swap_order` 有 **5 次**因此被重抽。
   - 其余类型以完整签名（状态/参数/耗时/操作人）是否变化为准。
   `noop_injections` 逐类单独报。**同时给出保守口径**：若把 5 次空操作算作未命中，
   总体为 111/125 = 88.8%、`swap_order` 为 15/20 = 75%——两个数都在证据文件里可复算。
3. **两个口径都报**：`hit_rate`（报告标记了该会话）与 `strict_rate`（命中了该类专属规则）。
   只报对自己有利的那个不叫验收。

### 4.3 硬负例：合法变化不该被报

| 硬负例 | 含义 | 实测被报 |
|---|---|---|
| `known_operator` | 改用基线里另一名操作人 | **0/15** |
| `short_session` | 截断为 2 步（浏览型会话本来就短） | **0/4** |

`short_session` 只截断"前两步都成功"的会话：若第 2 步恰好被拒绝，那截断后的序列
确实是"以拒绝收尾、没有后续"，报它是对的。把这类样本算进硬负例，等于要求检测器
放过一个真实问题。

## 6. 没达到的地方（如实列出）

1. **`drop_step` 只有 53%**。删掉一步后，剩下的相邻跳转往往仍在基线里存在
   （例如从"清单→回测→回测→对比"删掉一次回测，剩下的"回测→对比"是常见跳转）。
   顺序类规则对此天然无能；`prerequisite_missing` 只能补上"删掉的那步是前置动作"这一类。
   **要真正解决需要响应级信息**（例如把 `run_id` 写进工件，检查对比用的 id 是否本会话产生），
   属下一步改造，未在本轮实现。
2. **`swap_order` 本轮 100%，但存在结构性盲点**。语料里"两种顺序都常见"的相邻对确实存在
   （清单↔策略表，`browse` 与 `inspect` 两类会话各占一端）：交换它们时两个跳转都算"见过"，
   顺序规则报不出来。本轮 15 个样本恰好没抽到这一对，**不代表它不会发生**。
   另外，本轮有 5 次交换因"顺序视角未变化"被重抽——若把它们算作未命中，该类型只有 75%。
3. **`off_hours` 未启用**：单次构建语料跨度 0 小时。真实部署后需按自然日积累语料重建。
4. **`duration_outlier` 对组合回测停用**：基线 14 条样本 <20 门槛。门槛不降——降门槛等于
   用 18 个样本定义"正常耗时"。
5. **生产形态 0 命中**：同源语料的自比对，见 §5.3。
6. **语料不是历史**：见 §1.2。本文件所有命中率都是"在引导语料上"的命中率。

## 7. 关键取舍（别以后"顺手"改掉）

1. **只消费 T1 工件，不新增写入路径**。再记一份"给复盘用的日志"等于制造第二个真相来源。
2. **基线不足时规则停用，不降门槛**。否则报告会变成"样本越少、异常越多"的机器。
3. **`silent` 必须为 0**：每条规则只有三种状态（命中 / 启未命中 / 停用+原因），
   第四种状态（悄悄不存在）在验收里直接判失败。
4. **合成步骤的 `card_id` 用显式前缀**（`injected:synthetic:`），报告里一眼能分清
   哪些定位指向真实卡片。可回溯率只在真实卡片上定义。
5. **报告头部的"标记率"不叫"命中率"**：生产形态下它是"有多少会话被标记"，
   不是准确率，也不是真实异常率。措辞不精确的指标迟早被当成结论用。
