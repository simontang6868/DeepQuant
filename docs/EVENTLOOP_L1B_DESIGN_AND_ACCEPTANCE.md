## 1. 定位与能力边界

方案二（自研轻量事件驱动内核）要回答的只有一件事：

> 向量化粗筛（L1a）给的收益，在考虑**排队、部分成交、滑点、涨跌停**之后，还剩多少？

**能力边界必须最先读**：本仓库只有日线数据（`data/exec_all`、`data/qfq_all` 均为日频），没有分钟、没有逐笔、没有 L2 订单簿。因此：

- 事件的**时序与账务是真的**（结算 → 开盘 → 收盘 → 策略决策 → 估值，逐相位推进）；
- 成交的**细节是模型**（参与率额度、队列位置、冲击），不是对真实撮合的复现。

任何引用本内核的结论，都必须带上这一句。称它为"复现真实撮合"就是造假。

## 2. 架构

```
events.py   事件类型与同刻优先级（SETTLE < BAR_OPEN < BAR_CLOSE < SIGNAL < MARK）
clock.py    模拟时钟 + 确定性事件堆（拒绝回填过去的事件）
orders.py   订单状态机（非法转移直接抛错，终态不可复活）
account.py  账户记账（T+1 / 整手 / 费用走 compute_fees / 缺价拒绝估值）
matching.py bar 内撮合（价格可及性、额度共享、排队位置、部分成交、封板）
impact.py   滑点与冲击（NONE / CONSTANT / SQRT_IMPACT）
kernel.py   主循环装配
```

`gates/l1b.py` 在其上做闸门：复用 L1a 的 `HypothesisSpec` 与策略工厂，不另开参数入口。

### 2.1 每日事件相位

| 时刻 | 事件 | 做什么 |
|---|---|---|
| 09:00 | `SETTLE` | T+1 释放：昨日买入转为可卖 |
| 09:30 | `BAR_OPEN` | 撮合"开盘即可成交"的订单（市价单在此成交） |
| 15:00 | `BAR_CLOSE` | 撮合"盘中触价"的**限价单**（按限价成交） |
| 15:00 | `SIGNAL` | 策略用截至当日的数据出信号 → 生成次日订单；撤销当日未成交订单 |
| 15:30 | `MARK` | 日终估值快照 |

顺序写在 `events.PRIORITY` 常量里，不散落在调用处——因为"改了顺序"这件事必须显式且可被测到。`SETTLE` 晚于撮合会让 T+1 变成 T+0；`MARK` 提前会把未成交订单算进权益。

### 2.2 订单生命周期

`PENDING_NEW → ACCEPTED → PARTIALLY_FILLED → FILLED`，另有 `CANCELLED` / `REJECTED` 两个终态。终态不可复活——这是"已全部成交的订单被后续回报改成部分成交、持仓多算一次"这类静默错误的唯一防线。

订单只在执行日（T+1）当天有效，日终未成交即撤销。与日线引擎"一次执行机会"一致，避免订单跨日累积让成交量凭空增长。

## 3. 与日线引擎的关系

**相同**：都用 `Strategy.generate_signals` 出信号、都用 `BacktestConfig` 的计算费率、都是"T 日收盘信号 → 最早 T+1 开盘成交"、都做整手与 T+1、买入数量都按整手逐手回退。

**不同**：多了参与率额度、排队位置、部分成交、涨跌停。

**一处刻意的不一致**：日线引擎在完整样本上一次算完信号再裁剪；本内核在**每个交易日**用截断数据重新调用策略，只取最后一个信号。代价是 O(n²)，收益是**不可能偷看未来**——策略物理上拿不到未来的行。日线引擎依赖"策略实现是因果的"这一约定（由 L1a 的静态+动态泄漏检测兜底），本内核把它变成结构性保证。

### 3.1 对齐验收（最重要的一项）

把摩擦全关（`participation_limit=1.0, queue_position=0, slippage=NONE`、不提供封板表）后，两引擎必须逐笔一致：

| 指标 | 日线引擎 | 事件驱动内核 |
|---|---|---|
| 成交笔数 | 46 | 46 |
| 逐笔（日期/方向/数量/价格） | 完全一致 | 完全一致 |
| 期末权益 | 202,311.04 | 202,311.04 |

这条不成立，后面所有数字都不能用——因为差异里会混着"实现 bug"和"模型差异"两件事，无法归因。

## 4. 成交模型：三个参数与三条保守约定

| 参数 | 默认 | 含义 | 状态 |
|---|---|---|---|
| `participation_limit` | 0.10 | 单日最多吃掉当日成交量的比例，所有订单共享 | **模型假设，未标定** |
| `queue_position` | 0.5 | 触价未穿越时，队列里排在我们前面的量占额度的比例 | **模型假设，未观测** |
| `slippage_mode` | `none` | 无 / 常数 bps / 平方根冲击 | 主判定用 none |

三条保守约定（方向永远对交易者不利）：

1. **触价成交按限价成交**，不占用 bar 的更优价。当天最低价 9.0、限价 9.9，成交价就是 9.9，不是 9.0。
2. **队列位置 > 0 时压缩可成交量**，压缩比例等于队列位置。
3. **涨跌停只判"开盘是否被封死"**，不推断盘中是否打开；封死即不可成交。

### 4.1 涨跌停必须用交易层数据

涨跌停价 = 前收盘 ×(1±比例)，这个公式**只在复权价格上不成立**。用 qfq 价格算会把除权日的价格跳变误判成跌停——错误方向恰好会让大量除权日变成"跌停不可卖"。

因此内核接受的是**尺度无关的布尔标记**（`limit_up_hit` / `limit_down_hit`），由 `limits_from_trading_frame()` 从 `data/exec_all` 算出。策略价格用什么尺度都不影响判定。

若未提供封板数据，`limitations` 里会明确写"本次运行未执行涨跌停判定"——绝不因为"没提供"就当"没有涨跌停"。

## 5. L1b 判定链（顺序是设计的一部分）

```
契约 → 数据 → 基线收益>0? → ①成交率 → ②符号反转 → ③衰减 → ④成交价可解释 → PASSED
```

**为什么成交率必须先于符号反转**：成交率不足时收益必然退化。若先判符号，会把"没买到"误报成"策略失效"，归因就错了。这条是本轮实测踩出来的（首版顺序相反，一次全 0 成交的用例被报成 `SIGN_REVERSAL`）。

**为什么基线必须与精验同资金**：L1a 用 10 万跑出来的收益，放到 3000 万上精验，差异里混着"资金规模"和"成交摩擦"两件事。所以基线档 = 「同资金 + 摩擦全关」，精验档 = 「同资金 + 摩擦全开」，两者之差才是摩擦的净效应。

**前置门禁**：表 7 是逐级闸门。L1a 没放行时，L1b 即使各项都过，终态也只给 `L1B_BLOCKED_PREREQUISITE`——两档仍然跑完，但只为留下"摩擦吃掉多少"这个数字，不构成放行结论。

## 6. 验收（六项，全部实测）

| 验收项 | 结果 | 取证方式 |
|---|---|---|
| 无摩擦配置与日线引擎逐笔一致 | **PASS**（46 笔、权益末 202,311.04 相同） | 两引擎同数据同参数各跑一次，逐笔对比 |
| 终态覆盖无静默缺口 | **PASS**（覆盖 8/9，未覆盖项有正当理由） | 每类终态各跑一次；`UNEXPLAINABLE_PRICE` 正常路径不可达，用注入偏差证明核验有效 |
| 成交价核验能抓到偏差 | **PASS**（注入 5% 偏差 → 报 1 笔不可解释） | 干净样本 0 笔、注入样本 1 笔 |
| T+1 在账户层被结构性拒绝 | **PASS**（当日卖出抛 `InsufficientPosition`） | 买入后立即卖出，捕获异常信息 |
| 封板标记来自交易层且真实存在 | **PASS**（5140 日中 4 次涨停开盘、9 次跌停开盘） | `limits_from_trading_frame` 实算 |
| 资金敏感性跨过判定阈值 | **PASS**（1000 万 PASSED → 3000 万 REJECTED_FILL_RATE） | 四档资金各跑一次 |

## 7. 真实用例：ma_cross / 000001.SZ / 2016–2021

L1a 最优参数 `fast=3, slow=60`。主档资金 10 万（与粗筛一致），摩擦全开：

| 档位 | 累计收益 | 成交笔数 | 市场性成交率 |
|---|---|---|---|
| 无摩擦基线 | +1.0231 | 46 | 1.0000 |
| 事件驱动精验 | +1.0231 | 46 | 1.0000 |

保留率 1.0000 —— **10 万资金下摩擦完全不 binding**。终态 `L1B_BLOCKED_PREREQUISITE`（因为 L1a 已因回撤 32.84% 超限被拒）。

资金敏感性（参考，不参与主判定）：

| 资金 | 无摩擦收益 | 精验收益 | 保留率 | 市场性成交率 | 终态 |
|---|---|---|---|---|---|
| 100 万 | +1.0227 | +1.0227 | 1.0000 | 1.0000 | `L1B_PASSED` |
| 1000 万 | +1.0228 | +1.0228 | 1.0000 | 1.0000 | `L1B_PASSED` |
| 3000 万 | +1.0228 | +0.8254 | 0.8070 | 0.8649 | `L1B_REJECTED_FILL_RATE` |
| 1 亿 | +1.0229 | +0.7834 | 0.7659 | 0.4444 | `L1B_REJECTED_FILL_RATE` |

**这张表是本轮最有信息量的结果**：单标的、满仓、参与率 10%、队列 0.5 的假设下，1000 万以内摩擦几乎不咬人，3000 万时成交率跌破 90% 阈值，1 亿时近六成订单拿不到成交。注意这是**单标的**结果——分散组合会显著缓解，不能直接外推到组合层面。

## 8. 踩坑记录（都可复现，写下来避免重犯）

1. **`int` 与 `IntEnum` 用 `is` 比较恒为 False**。`_signal_for` 返回 `int`，判断用 `signal is Signal.BUY`，结果内核一笔不下单、还"跑得很干净"（0.2 秒结束）。修法：返回枚举本身。
2. **相位表漏了 `SIGNAL` 事件**。`SESSION_TIMES` 只有 4 个相位，策略根本没被调用过——但事件计数显示 1461 天全跑完，一切"正常"。修法：补 `("15:00", SIGNAL)`，靠优先级排在收盘之后。
3. **`HypothesisSpec` 没有 `execution` 字段**。契约里的执行假设在 `parse_spec` 时被丢掉，`to_dict()` 再序列化时已无此项 → **压力档实际拿到的是默认"无摩擦"配置**。这个 bug 最危险：它让人以为"已加压、结论是不敏感"，其实是根本没加压。修法：spec 增加 `execution` 字段，且为空时不写进 `to_dict`（否则会改变已冻结的 L1a `spec_digest`）。
4. **市价单在收盘被重复尝试**。日线模型下"当天没成交"就是没成交，收盘再试等于凭空制造流动性。修法：`BAR_CLOSE` 只处理限价单。
5. **资金不足缩量混进了成交率**。缩量是"钱不够买那么多"，不是"市场不给成交"；混在一起会让 L1b 把资金约束误判成流动性衰减。修法：单列 `cash_limited`，成交率分母剔除。
6. **断言写成"去重条数 == 用例数"**，看起来在验证终态覆盖，实际只验证了"用例互不相同"，7 个用例过了却漏掉 2 种终态。修法：与 `ALL_VERDICTS` 求差集，未覆盖的必须写明理由。
7. **差点留下假的核验函数**。首版 `_explain_prices` 直接 `return {"unexplained": 0}`——"成交价可解释"这项就永远是 PASS。修法：删掉，改用真实逐笔比对，并注入 5% 偏差证明能抓到。

前四条属于同一类：**程序跑通了、数字看起来合理，但做的事不是它声称做的事**。这类错误只能靠"两个独立实现对比"和"故意注入错误看能不能抓到"来发现。
