## 3. 1.3 调度可靠性的验收标准

### 3.1 行为要求（每项都要有可执行测试）

| ID | 要求 | 测试方式 |
| --- | --- | --- |
| **1.3-a** | `--dry-run` 必须**不写任何文件**（台账、targets、observations、心跳都不写），并打印将写入内容的摘要与 sha256 | 运行后比对目录 mtime 与文件集合；断言零新增零修改 |
| **1.3-b** | 已存在的台账**拒绝覆盖**；需 `--force` 且必须先备份旧件为 `YYYYMMDD.json.bak.<UTC时间戳>`，并在 `forward/corrections.jsonl` 追加一行 | 连跑两次：第二次必须非零退出并给出明确原因；加 `--force` 后旧件仍在（备份）、新件已写 |
| **1.3-c** | 补跑必须显式标 `--late-run`，记录 `late_run=true` 与 `late_trading_days`；**不得**用决策日之后的任何价格**计算信号** | 断言 `late_run` 字段存在；断言信号所用 `data_last_date <= decision` |
| **1.3-d** | 决策日判定必须与文档一致：**「该月最后一个交易日」即可用**，不得要求「该月之后还有数据」 | 构造「数据恰好止于某月最后一个交易日」的边界，断言返回该日而非上月 |
| **1.3-e** | 次一交易日未知时，成交状态必须是 `PENDING_NO_CALENDAR`，**禁止**用决策日自身当执行日判断成交 | 断言 `next_td` 为 None 时状态不是 `FILLED`/`NO_BAR` 而是 `PENDING_NO_CALENDAR` |
| **1.3-f** | 台账必须记录代码来源：`code_sha256`（脚本文件哈希）+ `git_head`（不可得时写 `NOT_IN_GIT`）+ `data_last_date` | 断言三字段存在且 `code_sha256` 与 `sha256(文件字节)` 相等 |
| **1.3-g** | 每次运行写心跳 `forward/heartbeat.json`（`ts`/`decision`/`mode`/`ok`/`duration_s`） | 断言运行后文件存在且 `ts` 递增 |
| **1.3-h** | `--verify` 只读自检：配置哈希、台账 `ledger_sha256` 链、`observations.csv` 与台账一致性；**不写任何文件** | 运行前后目录哈希不变；人为改坏一条台账后 `--verify` 必须非零退出 |
| **1.3-i** | **`p13b` 的 `selftest` 必须从台账 `counts_toward_observation` 推导**，不得由独立开关静默覆盖；显式 `--selftest` 与台账不一致时**报错退出** | 用现有 `20260930` 台账（SELFTEST）跑 p13b 不带参数，断言 track 的 `selftest=true` |

### 3.3 更正要求

`latest_closed_month()` 的改动**属于实现与文档不一致的修正，不是口径变更**：

- 文档原文（模块 docstring 与本文件 §3.1 1.3-d）：「决策日 = 最新**已完结**月份的最后一个交易日」
- 原实现：要求「该月之后存在数据」⇒ 永远取到上一个月 ⇒ **信号恒晚一个月**
- 影响面：当前只有 1 条 SELFTEST 记录、0 条 FORWARD ⇒ **无历史结论受影响**
- 处理：改实现 + 在 `forward/corrections.jsonl` 记一条，`reason` 写明「原实现使信号恒晚一个月，与文档不一致」
