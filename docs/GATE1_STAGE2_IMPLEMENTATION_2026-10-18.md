## 2. 授权闸门：为什么写在代码里而不是文档里

预登记 §17 第 5 项是「用户授权」。这一项如果只写在文档里，它不会阻止任何人——包括我自己——敲一次回车。

所以闸门做成了**两个条件同时满足**：

```
--execute            且            --authorized-by "<用户授权原话>"
```

`--authorized-by` 的校验不是「非空即可」：

- 长度 < 10 字符 → 拒绝
- 命中占位符（`TODO` / `TBD` / `xxx` / `test` / `placeholder` / `待定`）→ 拒绝
- 拒绝信息里写明「这一项要求记录用户授权原话，用于审计『协议先于结果』」

**实测验证**（不是看代码推断）：

| 命令 | 结果 |
|---|---|
| `--execute` | 退出，提示「Gate 1 第二阶段需用户明确授权」。**由于校验在 `load_prices` 之前，连数据都没读**（输出里没有 `[LOAD]`） |
| `--execute --authorized-by "TODO"` | 退出，提示占位符不算授权 |
| 两次拒绝后 `gate1_out/` | **未被创建** |

还有一道：`ensure_no_overwrite()` —— 同一 `run_id` 目录已有 `summary.json` 就拒绝覆盖。理由写在代码里：预登记 §12.5 把「同配置两次运行必须一致」当作可复现性证据，覆盖会让第一次的结果消失，那条证据就永远无法复核。

## 3. 判据代码化：三个必须自己做的决定

### 3.1 t 分布不能近似

本机没有 scipy，硬约束又禁止为此加依赖。用正态近似看起来省事，但 df=48 时 t 分布尾部比正态厚，**p 值会系统性偏小**，直接影响 BH 校正下「有几组能存活」。而 BH 结论正是敏感性分析的全部内容。

所以自带正则化不完全贝塔函数（Lentz 连分数），用两个有**解析解**的特例钉死：

| 自由度 | 解析解 | 测试断言 |
|---|---|---|
| ν=1（柯西） | `P(|T|>1) = 0.5` 精确 | `approx(0.5, abs=1e-12)` |
| ν=2 | `P(|T|>t) = 1 - t/√(2+t²)`，t=1 时 `= 1-1/√3` | `approx(1-1/√3, abs=1e-12)` |

正态近似在这两点都给 0.317，与 0.5 差一个量级——测不过就说明实现写错了。另加一条：df=47, t=2.0 的 p 必须落在 (0.0500, 0.0520)，因为临界值 `t_{0.975,47}=2.0117` 略大于 2.0。

### 3.2 BH 校正的单调性

`q_(i) = min_{j>=i} (p_(j) · m / j)` —— 必须取**右侧最小值**。少了这一步会出现「p 更小但 q 更大」的自相矛盾输出。测试专门用 12 个递增的 p 值验单调性。

### 3.3 协议没写清的一处：本实现的显式解读

预登记 §10.2 写「证据不足 = 不属于上述两档，**或**任一情形发生（创业板影响 / 600809 纠缠 / 成本转负）」。字面上没说这些情形与「失败」档谁优先。

**本实现取 `失败 > 证据不足 > 成功`：**

- 满足失败条件 → 一律判失败，`insufficient_flags` 不改变它。理由：所有近似项（涨跌停偏松、停牌近似）的方向都是让策略**看起来更好**；在这种偏差下仍然显著跑输，真实无效的证据只会更强。
- 满足成功条件但 flags 非空 → **降级为证据不足**。
- 其余 → 证据不足。

这个方向是保守的：flags 只能降级成功，不能升级失败。**解读写在代码的 docstring 里，不是写在报告里**——写在报告里等于事后可以挑一个方便的版本引用。

两个方向都有测试：`test_insufficient_flags_downgrade_success` / `test_insufficient_flags_do_not_upgrade_failure`。

## 4. 涨跌停：组合层做不到 board 模式，取 10% 而不是 20%

这是本轮唯一一处**实现能力低于协议要求**的地方，必须说清。

预登记 §6 写的是 board 模式（创业板/科创板 20%，其余 10%）。但 `PortfolioBacktestConfig` 的涨跌停来自 `fee_config.market_rules.price_limit`，而 `MarketRules.price_limit` 是**标量**——组合层没有 per-symbol 通道。50 只票共用同一个比例。

只剩两个选择：全体 10%，或全体 20%。我选 **10%**，理由是三个事实叠加：

1. 池子 **41/50 是主板**，10% 对多数标的是**正确值**；
2. **2020-08-24 之前创业板真实就是 10%** —— flat 10% 在那一段同样正确。预登记原本担心的乐观偏差（「2020 前按 20% 太松」）恰好被消除了；
3. 只在 2020-08-24 之后对 9 只双创标的偏严（本该能成交的被挡）→ **悲观方向**，不会高估策略的成交能力。

反过来用 20%，会让 41 只主板**永久偏松**（本该被挡的涨跌停日照样成交）——那正是预登记想避免的乐观偏差，而且是长期、系统性的。

这条会在真跑时写进 `summary.json` 的 `price_limit_rate` 字段，也写进 dry-run 输出的 `price_limit_note`，最终报告必须重申。

> **附带的好处**：预登记 §10.2 要求「创业板涨跌停无法实现被证明有实质影响 → 判证据不足」，判定方式是「把 2017~2020 的创业板移出候选池后重跑，符号翻转即视为实质影响」。S11（仅主板）正好是这个判定，已实现在 `main()` 里自动执行——**不靠人看，靠代码判**。

### 5.1 S6 的集中度风险（必须在报告里提示）

top10% 在候选 33~50 只时，`ceil(n×0.1)` = 4~5 只，单只权重 **20~25%**。这不是 bug，是 `top_fraction=0.1` 的固有性质。

但它带来一个解释陷阱：**若 S6 的超额显著高于其他组，更可能是「4 只票的集中度」而不是「动量更有效」。** 这类结果不得作为「应该改主实验参数」的依据（预登记 §11 已明令禁止「S6 表现最好所以主实验应该用 top10%」）。

### 5.2 2024-12-31 的信号没有执行日

`month_end_signal_dates` 返回 96 个信号日，最后一个 2024-12-31 之后没有交易日，故 `unmatched`，不生成订单，写入 `data_quality_issues`（**不是静默丢弃**）。

这是正确行为：执行 2024-12 的信号需要 2025-01 的行情，那是未来数据。2024-12 的月度收益仍然存在（来自 2024-11 月末的持仓）。

## 6. 统计口径：R12 的落点

`monthly_returns()` 只吃 `PortfolioState.total_equity`（连续净值），月末取最后一个有效值，月收益 = 本月末 / 上月末 − 1。

- **不用窗口级独立收益**。B20 的教训在这里：窗口级收益之和 ≠ 连续账户收益。
- 判定窗口按 `eval_end` 截短，S12 正是靠这个只取 2021-01~2022-12。
- 策略与基准的月度索引**必须逐日相同**（共用同一日历），不一致直接抛错而不是取交集静默对齐。
- `total_equity is None` 的日期被跳过但不断链——有测试覆盖。

## 7. 敏感性结果的四类自动判定

真跑完成后，`main()` 会自动做两件「人容易偷懒」的事：

1. **S11 与主实验符号不一致** → 追加 flag「排除创业板/科创板后符号翻转 → 无法实现的涨跌停约束可能有实质影响」。
2. **S9 由正转负** → 追加 flag「成本提到 high_cost 后 mean(d) 由正转负」。

这两条在预登记 §10.2 里是「证据不足」的触发项。写成代码而不是留给报告作者判断，是因为这两条恰好是**最容易被忽略的**——它们都在结果不理想时才触发，而那时人的注意力全在「为什么不好」。

第三项（600809 纠缠）需要额外跑一版「排除 600809」的对照，**未在本轮实现**。若真跑后主实验与 S11 符号一致、且 S9 未转负，则该项不影响判定；否则需要单独补跑并在报告中声明。
