## §3 程序结构（用于判断"是不是个黑盒"）

程序分为四层，职责不重叠：

| 层 | 模块 | 职责 | 是否直接报单 |
| --- | --- | --- | --- |
| 信号层 | `research/.../p13_forward.py` | 每月末根据行情数据算出目标持仓 | 否 |
| 规划层 | `execution/planner.py` | 目标持仓 → 差额订单（先卖后买、整手取整、幂等编号） | 否 |
| 风控层 | `execution/risk_gate.py` | 11 条硬性限制，任一不过即拒 | 否 |
| 接口层 | `broker/` | 与券商交互（下单、撤单、查询） | **是**（唯一一层） |

**唯一的报单出口是接口层。** 上层没有任何绕过路径可以发单——这一点由代码结构保证，不只是约定。

代码规模：`backend/src/deepquant` 共 188 个 Python 文件；其中执行与接口两层合计 3,888 行，是本次申报相关的核心部分。

## §4 报单流程与安全检查

每一次委托在发出前依次经过以下检查，**顺序固定、停在第一个失败**：

```
停机开关 → 熔断 → 授权文件 → 上一轮对账 → 状态未知委托
→ 交易时段 → 黑名单 → 行情新鲜度 → 价格偏离
→ 单票上限 → 单笔金额 → 单日笔数
```

顺序本身就是规则：先问「这个系统还该不该发单」，再问「这笔单合不合规」。一个已经熔断的系统不会继续讨论单笔金额大小。

配套的安全机制：

| 机制 | 说明 |
| --- | --- |
| 授权文件 | 必须存在且未过期，包含金额上限、可用板块、有效期。文件不存在即拒单 |
| 熔断 | 组合峰值回撤 −2.5% 即停止发单；峰值持久化，重启不丢 |
| 停机开关 | 文件或命令触发即停止，不自动恢复 |
| 状态未知委托 | 存在状态未知的委托时**禁止发任何新单**，直到以券商返回数据重建并确认 |
| 日终对账 | 持仓、资金、成交、委托四类对象逐字段比对；任一差异即停机 |
| 台账 | 每笔决策/委托/成交/成本分项全部落盘，只追加并带哈希链，历史行被改可被检出 |

## §6 已知限制与风险（如实列出）

1. **未接入真实券商接口**。当前与券商交互的部分是"可注入故障的模拟实现"，用于在无接口时验证逻辑。真实适配器需在取得接口后按券商文档实现。
2. **单机运行，无高可用**。关机、休眠、断网都会导致漏跑；程序无远程唤醒能力。程序允许补跑 3 个自然日，超出则该期观察记录作废。
3. **无实时行情**。当前只有日线与每日快照，无 Level-2 盘口；委托价按「最新价 ±0.3%」近似对手价，投产初期需用真实成交价校准。
4. **交易日历靠历史数据推导**。未来交易日不可知，「次一交易日」在当日只能是推断。
5. **未做压力测试**。没有在真实接口上验证过连续报单、断线重连、部分成交回报延迟等情形。
6. **限速器未接入运行时**。`execution/rate_limit.py` 已实现并有测试，但尚未接进发单循环（当前无发单循环）。详见 `02_申报速率与单日笔数上限.md` §5。
