## 2. 修复方案（R7 2a–2f ＋ Q2 三点）

### 2.1 文件布局与解析（2a）

- 每日快照写入 **`forward/account_snapshot_YYYYMMDD.json`**；多版本为 `account_snapshot_YYYYMMDD_rev<N>.json`（rev1 为无后缀或显式 `rev1`，**统一采用显式 `rev1` 以免歧义**）。
- 另写 **`latest.json` 指针**：`{"day":"YYYYMMDD","path":"...","rev":N,"sha256":"...","updated_at":"..."}`，**原子写入**（`tempfile` 同目录 + `os.replace`），**不使用符号链接**（Q2-b）。
- **SHADOW 按 `day` 直接解析目录**（`glob(f"account_snapshot_{day}*.json")`），**完全不依赖 `latest.json`**；`latest.json` 只供运维/备份定位。
- 输出中记录 `account_rev` 与 `account_sha256`，便于复算。

### 2.2 迁移（2b、Q2-c）

1. **复制**新增 `account_snapshot_20261109_rev1.json`，内容取自现有 `account_snapshot.json`（`asof=20261109`）；**不 mv、不删、不改原文件**。
2. 原 `account_snapshot.json` **冻结**（只读留痕，不参与运行）；记录其 sha256 与迁移前后各文件 sha256。
3. 校验：迁移副本的规范化内容与原件一致；重复执行迁移**幂等**（已存在且内容相同 ⇒ 不重写、不改 mtime）。
4. **11-10 起至修复上线前每日 `rc=4` 的日子一律按「缺失」处理，不补写**；20:34 的只读探针是**事后快照**，**不得**用于补写（Q2-c）。这些日子不作为 G2 起算日。

### 2.3 同日不同内容与多版本（2d、2e、Q2-a）

- 同日重跑且内容不同 ⇒ **拒绝 + 告警 + 非零 rc**（`EXIT_CONFLICT`），不静默覆盖。
- 仅显式 **`--supersede <原因>`** 才生成 `rev2`，并在文件内记 `supersede_reason`、`supersedes_rev`、`created_at`。
- SHADOW 默认读该日**最新 rev**（按 rev 号最大），输出记所读 rev 与 sha。
- **G2 计入条件收紧**：该日只有 1 个 rev，**或**所有 rev 的账户内容（`cash` + `positions`）完全一致 ⇒ 才可能计入；否则 `mode=SELF_CHECK_ONLY`、原因码 **`REV_CONFLICT`**、`counts_toward_g2=false`，待人工复核。

### 2.4 快照时点（2f，确认前不动调度）

- 不预设固定时点。先在 **15:30 / 16:30 / 17:10 / 18:00** 用只读探针取账户状态；**有成交的交易日**观察状态稳定时点，**零成交期间只记录不结论**。
- 据此提出「快照时点与调度调整方案」，包含：快照后是否重跑 SHADOW／备份／邮件；17:40 告警须**晚于全部阶段**。
- **方案交用户确认；确认前保持现有调度**。快照元数据新增 `collected_at`（采集时刻）与 **`settlement_verified=unknown`**。

### 2.5 rc 收紧口径（R7-3、Q3，见第 3 节清单）

关键阶段（行情增量、宇宙快照、决策、账户快照、SHADOW、备份）**任一非零 ⇒ `stage_ok=0` ⇒ 心跳 `ok=false` ⇒ 17:40 告警 ⇒ 该日不计 G1**。17:40 告警改为**读取阶段结果文件**，不只读 `ok` 字段。
