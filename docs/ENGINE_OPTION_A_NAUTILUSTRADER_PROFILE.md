## 1. 这个方案要解决的问题

上位文件 §4.1 指出我方在策略验证链路上存在两处结构性缺口：

**缺口一：研究—生产漂移。** 回测代码与实盘执行代码由两套实现分别维护，长期各自演化；回测结论迁移到实盘后出现偏差却难以归因。注意这里的措辞——不是"回测不准"，而是**偏差出现后无法归因**，因为两侧实现不同，差异来源不可枚举。

**缺口二：执行成本建模缺失。** 对滑点、成交概率、延迟的假设停留在常数层面（本项目 `BacktestConfig` 的 `slippage_buy/sell` 就是常数比例），无法支撑对执行敏感型策略的评估。

这两个缺口正是 L1b 闸门要回答的问题，也是本方案的价值主张所在。

## 2. 四类候选的定位（上位文件表 4，2026-10-27 核实）

| 候选 | 定位 | 协议 | 活跃度 | 关键能力 | 结论 |
|---|---|---|---|---|---|
| **NautilusTrader** | 生产级事件驱动引擎 | LGPL-3.0-or-later | 高 | 回测与实盘复用同一套策略代码、纳秒级时钟、多资产、Rust 核心 | **建议立项评估** |
| vectorbt | 向量化参数扫描 | Apache-2.0 + Commons Clause | 低（开源版仅修缺陷） | 数千组参数秒级扫描 | 仅用于粗筛，不进入生产 |
| LEAN | 全栈平台 | Apache-2.0 | 高（约 22.2K 星） | 多资产回测、云回测、二十余家券商直连 | 不引入（券商覆盖以海外为主） |
| HftBacktest | 高频执行仿真 | MIT | 低（近六个月无提交） | 全订单簿重建、双延迟建模、队列位置成交模拟 | 只借鉴方法论，不引入 |

两条判断依据（上位文件原文要点）：

1. **维护状态优先于社区规模**。向量化引擎开源版已进入仅修缺陷状态，限价单、杠杆、并行化在商业版——作为生产依赖会撞能力天花板。"是否持续发版"比"累计关注度"更能预测三年后的可用性。
2. **协议的传染性差异决定集成方式**。LGPL-3.0 允许专有代码以链接方式使用，仅要求回馈对引擎本身的修改；带 Commons Clause 的协议禁止把软件作为产品主体销售。两者处理路径不同，须在选型阶段而非集成阶段厘清。

### 3.2 架构（官网 crate 清单，2026-10-24）

Rust 核心 + Python 绑定，拆为 **22 个核心 crate + 12 个 adapter crate**，依赖流向为「核心 crate ← adapter crate」。对评估有意义的几个：

- `nautilus-trading`（策略机制）、`nautilus-execution`（订单管理）、`nautilus-portfolio`（组合）、`nautilus-risk`（风控）——**这四个正好对应"回测/仿真/实盘三模式复用"的落点**
- `nautilus-backtest` 与 `nautilus-live` 并列为两个 system 层 crate，说明回测与实盘确实共享同一套引擎内核，而非两套实现
- `nautilus-event-store`（事件溯源与重放）、`nautilus-persistence`（Redis/PostgreSQL）——对 T1 审计留痕有参考价值
- `nautilus-testkit`、40,000+ 自动化测试（含 property-based 与 simulation），是其可信度的主要依据

### 3.3 成交与延迟模型：**关键事实，直接修正了"换引擎就有保真"的预期**

第三方对 v1.231.0 源码（`backtest/models/fill.pyx`）的核对显示，`FillModel` 默认参数为：

| 参数 | 默认值 | 含义 |
|---|---|---|
| `prob_fill_on_limit` | **1.0** | 市价触及但不穿越限价时，**永远假设自己在队首** |
| `prob_slippage` | **0.0** | 一档逆价滑点概率为 0，默认**零滑点** |
| `random_seed` | `None` | 随机过程不可复现，两次"相同"回测会给出不同结果 |

也就是说：**开箱即用的配置是乐观的**——完美队列位置、零滑点。它的价值不在于"默认保真"，而在于**提供了一整库可配置模型**：`prob_fill_on_limit`、`SizeAwareFillModel`、`VolumeSensitiveFillModel`、`CompetitionAwareFillModel`、`LimitOrderPartialFillModel`、`TwoTierFillModel` 等十余种，以及 `LatencyModel`（base / insert / update 三段纳秒延迟）。

**这条事实对 K5 对比的影响**：D3（成交保真度）不能因为"NautilusTrader 有 FillModel"就给它满分。**两边都必须显式配置模型**；差别在于"模型库的丰富度与实现质量"，而不在"有没有保真能力"。若我方自研只做 2–3 个模型，那是覆盖度差距，不是有无差距。

另需注意：`random_seed=None` 时回测不可复现——本项目"结论必须可复现"的要求与默认配置冲突，必须显式设种子。这与项目 R3（不编造）同源。

### 3.4 环境与打包（对"适配成本"有直接影响）

| 事实 | 对本项目的含义 |
|---|---|
| 需要 **Python >= 3.12** | 本项目 `requires-python = ">=3.12"`，实测环境 **3.13.14** → **不构成障碍** |
| 有 Windows / macOS / Linux 预编译 wheel | 实测环境 Windows 11 AMD64 → 可直接装，无需编译 Rust 核心 |
| **无 macOS x86_64 wheel**；manylinux_2_35（Ubuntu 22.04 级）为 glibc 底线；无 musllinux wheel | 若后续迁 Linux 容器，Alpine 与老发行版需从源码编译 |
| 两套精度模式（128-bit 默认 / 64-bit），**ABI 不兼容** | 跨模式不可混用；A 股价格精度用 64-bit 足够，但需在项目初就定死 |
| 适配器矩阵以海外与加密为主：OKX、Deribit、dYdX、Kraken、Coinbase、Databento、Tardis、Polymarket、Lighter、Binance 等 | **无 A 股券商/行情适配器** → "适配"维度的自研工作量是结构性的，不是配置问题 |
| 2.0 线将 `FillModel` 改名为 `DefaultFillModel`，导入路径从 `nautilus_trader.backtest` 迁至 `nautilus_trader.execution` | 1.x 写的代码在 2.0 需改导入；升级有迁移成本 |

### 3.5 许可义务（LGPL-3.0-or-later）

- 动态链接未修改的库：自有策略代码可保持专有
- 修改了 nautilus 本身：须发布修改，且**必须允许用户 relink**
- 贡献者需签 CLA（影响"能否给上游提 PR"）
- 上位文件表 5 的通过条件是**法务书面意见**，明确"无需开源自有策略代码"——这是唯一需要外部资源才能闭环的一项

## 4. 立项评估四维清单（上位文件表 5）+ 已知前置判断

| 维度 | 评估内容 | 通过条件 | 落档时的已知信息（未做实测，仅记录） |
|---|---|---|---|
| 合规 | LGPL-3.0 在"专有系统链接使用、不分发修改版"场景下的义务 | 法务书面意见 | 需外部法务资源；技术侧已可确认"以依赖方式使用、不回馈修改"路径存在 |
| 适配 | 存量通道与行情源的适配器自研工作量 | 完成最小适配器原型，跑通单标的回测 | **适配器矩阵无 A 股**，工作量为结构性；需自研行情 + 执行适配器 |
| 保真 | 同策略同区间在自有引擎与该引擎上的成交价、滑点、收益差异 | 差异可解释、可归因，无系统性偏差 | **需要参照物**——这正是先做方案二的理由；且其默认模型是乐观的（§3.3），必须显式配置才可比 |
| 成本 | 学习曲线与上手周期 | 两人三周内可产出可运行策略 | 第三方一致反映文档是短板、易用性评分偏低；两人三周为预算上限 |

**结论性判断（留档观点，非实测）**：四维中"合规"需外部法务、"适配"需自研适配器、"成本"有明确时间盒，唯一必须靠对我们自己代码的对照才能判的是"保真"。因此方案二的产出同时是 L1b 的载体**和**方案一"保真"维度的测量工具——这是把顺序定成"先二后一"的核心理由（见 `ENGINE-PLAN-001` §3）。

## 5. 若启动，两人三周怎么排（供后续决策直接复用）

前提：独立隔离环境，不接生产通道，不接券商，不注入真实账户。

| 周 | 人 A（工程） | 人 B（策略与合规） | 周末产出 |
|---|---|---|---|
| W1 | 装环境、跑通官方回测示例；用自有日线数据写最小行情适配器（CSV → Parquet catalog）；跑通单标的、单策略 | 通读 backtest/execution 文档；整理 FillModel / LatencyModel 参数清单与我方配置映射；发起法务咨询 | 单标的回测可运行；参数映射表；法务问题清单 |
| W2 | 写最小执行适配器（模拟撮合，不接真实券商）；把 `ma_cross` 移植为一个 `Strategy` 子类 | 用同一策略、同一区间、同一费率口径在**双方**引擎上跑；对齐无摩擦配置（零滑点/零费率/100% 成交） | 两引擎在无摩擦配置下差异收敛（或不收敛的原因定位） |
| W3 | 打开滑点与部分成交模型，做敏感性；整理性能与可维护性笔记 | 写评估报告四维结论 + 迁移成本估算；准备"通过 / 不通过"两版建议 | 四维结论 + 是否立项的建议 |

**验收门槛**：W2 结束若无摩擦配置下两引擎差异不能收敛，**直接判不通过**——因为这说明至少一方有实现问题，继续加模型只会掩盖。

**预算**：6 人周。这是本轮不启动它的直接成本理由——同样的 6 人周放在方案二上，产出的是可长期持有的 L1b 载体。

## 6. 风险与未知（留档时必须写清，否则对比时会忘）

| 类型 | 内容 |
|---|---|
| 已知风险 | ① 适配器需全部自研，A 股规则（T+1、涨跌停、ST ±5%、整手、停牌）需在适配层重建，可能重演"两套代码"问题 ② 2.0 线在 RC，1.x → 2.0 有导入迁移 ③ 默认模型乐观（§3.3），不配置就得到虚高结果 ④ 文档是公认短板，学习曲线陡 ⑤ 星标/版本会漂移，不可作为唯一依据 |
| 未知（必须实测才能答） | ① 同策略在两引擎的收益差异量级 ② 自研行情适配器到可用需几天 ③ 其事件循环在**日频单标的**场景是否有价值（事件驱动的复杂度在日频下可能纯属开销） ④ Windows 下的稳定性与性能（官方主要面向 Linux 部署） |
| 与本项目的接口未知 | T1 审计、T2 风控网关、T4 能力契约能否与其事件总线共存；若不能，"与现有系统集成成本"会显著上升 |

**第 ③ 条值得单独强调**：本项目的策略全是日频、单标的或横截面组合，没有盘中挂单需求。事件驱动引擎的复杂度（消息总线、状态机、时钟）在日频下的收益主要是"结构清晰"，而非"性能"或"保真"。这一点在 K5 里要如实计入 D3/D6，不能因为"它是生产级引擎"就默认更优。

## 7. 与方案二的可借鉴点（若最终不立项，这些仍然要拿）

1. **三模式复用同一策略类**的架构约束——方案二照此设计（同一 `Strategy` 接口同时被回测与仿真驱动）
2. **FillModel 参数化**的思路——把"成交概率、排队位置、滑点"做成可替换组件，而不是写死在撮合逻辑里
3. **LatencyModel 三段式**（base / insert / update）——比单一常数延迟更可解释
4. **事件溯源**（`nautilus-event-store`）与 T1 审计留痕同源，可对照检查我们的工件结构
5. **显式随机种子**——凡涉及随机的模型必须可复现
